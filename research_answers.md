1. Preserving State in HTTP Applications

HTTP is a stateless protocol, which means that each request sent by a browser is treated independently. By default, the server does not automatically remember information from previous requests. Web applications therefore use mechanisms such as cookies, sessions, and authentication tokens to preserve state across multiple request-response cycles. A cookie is a small piece of data stored in the user’s browser and sent back to the server with later requests. Cookies may contain a session identifier, preferences, or other limited information. In Django, session data is usually stored on the server, while the browser stores only a session ID in a cookie. When a request is received, Django uses this ID to retrieve the correct session information. This allows the application to remember details such as whether a user is logged in, the contents of a shopping cart, or temporary form information. Authentication builds on this process by linking a valid session to a particular user account. Django provides built-in authentication and session middleware to manage these features securely. Important protections include secure cookies, session expiry, password hashing, HTTPS, and protection against cross-site request forgery. These mechanisms allow a stateless HTTP application to provide a continuous and personalised user experience.

2. Migrating a Django Database to MariaDB

Migrating a Django application from SQLite to a server-based relational database such as MariaDB requires several configuration and deployment steps. First, MariaDB must be installed on the target server, and a database and database user must be created with appropriate permissions. A compatible Python database driver, such as mysqlclient, must then be installed in the Django virtual environment because Django uses the MySQL backend for MariaDB connections. The DATABASES setting in settings.py must be changed from SQLite to django.db.backends.mysql, with values for the database name, username, password, host, and port. Sensitive credentials should preferably be stored in environment variables rather than directly in source code. Before migration, the existing project should be backed up. If data already exists in SQLite, it can be exported with Django’s dumpdata command and later imported using loaddata. The developer should then run python manage.py makemigrations to confirm migration files are current and python manage.py migrate to create the required tables in MariaDB. Afterward, existing data can be loaded, and the application should be tested for database connections, model operations, character encoding, permissions, and production settings. Regular backups and restricted database privileges should also be configured.
